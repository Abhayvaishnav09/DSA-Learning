# 03. Frontend

## 1. Goals

- First lesson interactive in **< 2 s** on a mid-range Android phone over 4G.
- Feedback on non-code answers in **< 100 ms** (no network wait).
- Works offline for lessons already downloaded and for reviews.
- Accessible (WCAG 2.2 AA), bilingual (English, Hinglish), light and dark themes.
- A visualizer that makes logic *visible*: the core differentiator.

## 2. Stack

| Concern | Choice | Why |
|---|---|---|
| Framework | **Next.js** (App Router) + React + TypeScript strict | SSR/RSC for fast first paint and SEO on marketing and concept pages; client islands for interactivity |
| Styling | Tailwind CSS on top of design tokens (CSS variables) | Fast iteration; tokens keep themes consistent |
| Primitives | Radix UI (headless, accessible) wrapped in `packages/ui` | Accessibility done right; our own look |
| Server state | TanStack Query | Caching, retries, optimistic updates, offline mutation queue |
| Client state | Zustand (small global UI state) | Simple; no boilerplate |
| Complex flows | **XState** state machines (lesson player, hint ladder, code run) | Lesson flow has many states; machines make them explicit, testable and visualisable |
| Forms | React Hook Form + Zod (shared schemas from `contracts`) | One validation source |
| Animation | Motion (Framer Motion) + SVG | Declarative, interruptible animations for the visualizer |
| Code editor | **CodeMirror 6** | Smaller than Monaco, works well on mobile, accessible |
| Code run | Web Workers; Pyodide for Python | Off main thread; no server round-trip |
| Offline | Service worker (Serwist/Workbox) + IndexedDB (Dexie) | Cache content bundles; queue attempts |
| i18n | `next-intl` with ICU messages | Plurals, gender-neutral phrasing, locale routing |
| Charts (progress) | Lightweight SVG components; a chart lib only in admin | Bundle size |
| Testing | Vitest + Testing Library, Playwright, Storybook + visual regression | See [11-quality-testing](11-quality-testing.md) |

## 3. Rendering strategy

| Route | Rendering | Notes |
|---|---|---|
| `/` landing, `/learn/[concept]` public concept pages | Static (ISR) | SEO: "what is a loop, explained simply" |
| `/app` home, map | Server Components + streaming, client islands | Personal data fetched on the server with the session cookie |
| `/app/lesson/[id]` lesson player | Client component tree inside a server shell | Heavy interactivity; content bundle prefetched |
| `/app/review` | Client, works offline | Uses local FSRS + IndexedDB |
| `/admin/*` | Client, code-split, behind role check | Never in the learner bundle |

## 4. Application structure

Feature-sliced layout inside `apps/web/src`:

```
app/                    Next.js routes (thin: compose features)
features/
  lesson-player/        machine, beats (Story, See, Predict, Do, Explain), hooks
  items/                one renderer per item type (arrange, predict, fill, trace, truth-table, code)
  review/               due queue, review session
  map/                  concept graph view
  progress/             streaks, goals, achievements
  auth/                 sign-in, guest merge
  tutor/                (R3) AI chat panel
entities/               user, concept, item, attempt (types + query hooks)
shared/
  api/                  generated client + TanStack Query wrappers
  offline/              IndexedDB stores, sync engine
  i18n/, analytics/, flags/, lib/
```

Rule: `features` may import `entities` and `shared`; never another feature. Enforced by lint.

## 5. Lesson player (state machine)

```
idle ─► loading ─► story ─► see ─► predict ─► do ──► explain ─► complete
                              ▲                │  ▲
                              └─ replay ───────┘  │ wrong ─► feedback ─► (hint1→hint2→hint3) ─► do
```

- Each beat is a component with a typed contract `{ content, onDone(result) }`.
- The machine emits analytics events on every transition, so we see exactly where learners drop.
- Progress inside a lesson persists locally, so a refresh or app switch resumes on the same beat.

## 6. Visualizer engine (`packages/visualizer`)

The visualizer is a **deterministic frame engine**:

```
Program (authored steps or traced code)
   └─► Frames[] = { state: {vars, arrays, pointers, stack, output}, line: n, caption: i18nKey, highlight: [...] }
          └─► Renderers: VariablesBox, ArrayStrip, PointerArrows, StackView, TreeView, GraphView, TruthTable, Flowchart
```

- **Two sources of frames:** hand-authored for Stages 0 to 2; auto-generated by tracing real JS/Python code in a worker for Stage 3+ (instrumented interpreter emits a frame per line).
- Controls: play/pause, step forward/back, speed, scrub bar. Keyboard: Space, ←, →.
- Every frame has a text caption, so the screen-reader and low-bandwidth mode use the same data.
- `prefers-reduced-motion` respected: transitions become instant cross-fades.
- Rendering in SVG (crisp, accessible). Canvas fallback only for very large graphs (> 200 nodes).
- Renderers are tested with snapshot frames + Storybook stories.

## 7. Item renderers

Each item type is a plugin:

```ts
interface ItemRenderer<T extends ItemType> {
  type: T;
  Component: React.FC<{ item: Item<T>; onSubmit(answer: Answer<T>): void; disabled: boolean }>;
  // grading lives in packages/grader, not here
}
```

Types for R1: `mcq`, `predict-output`, `arrange-steps`, `fill-blank`, `trace-table`, `truth-table`, `explain-why`. R2: `code`.
Drag-and-drop (arrange) uses `dnd-kit` with full keyboard support.

## 8. Data fetching and sync

- All API calls go through the generated typed client. No hand-written `fetch` in features.
- Mutations (attempts, hint use) are **offline-first**: written to IndexedDB, shown optimistically, synced by a background sync engine with idempotency keys and exponential backoff.
- On conflict, the server is the source of truth for mastery and review schedule. The local copy is replaced after sync.
- SSE connection for live updates (mastery changed, concept unlocked). Reconnects with `Last-Event-ID`.

## 9. Design system (`packages/ui`)

- **Tokens:** color (semantic: `--surface`, `--text`, `--accent`, `--success`, `--danger`), spacing (4 px scale), radius, type scale, motion durations. Defined once and exported to CSS variables and TS.
- **Themes:** light, dark, high-contrast. Colour-blind-safe palette for correct/wrong (paired with icons).
- **Typography:** one variable font for UI, one monospace font for code; Devanagari-capable fallback.
- **Components:** Button, Card, Sheet, Dialog, Tabs, Toast, Progress, Streak, ConceptNode, CodeBlock, Hint, Feedback.
- Every component has Storybook stories for all states and themes, plus automated a11y checks (axe) in CI.

## 10. Performance budget (enforced in CI)

| Metric (p75, mid-range Android, 4G) | Budget |
|---|---|
| LCP | < 2.0 s |
| INP | < 200 ms |
| CLS | < 0.05 |
| JS on lesson route (gzip) | < 170 KB initial (CodeMirror and Pyodide lazy-loaded) |
| Pyodide | Loaded on first Python code item, cached by service worker |

Techniques: RSC to keep data-fetching code off the client, route-level code splitting, `next/font`, image optimisation, prefetching the next lesson bundle during the current one, Lighthouse CI + bundle size checks on every PR, real-user monitoring (web-vitals → analytics).

## 11. Accessibility checklist

- Full keyboard path through every item type (including drag-and-drop).
- Focus management on beat transitions; live regions announce feedback.
- Contrast ≥ 4.5:1; touch targets ≥ 44 px.
- Screen-reader text for every visual frame.
- Tested with axe in CI and manually with NVDA + TalkBack each release.

## 12. Security on the client

- Strict Content Security Policy with nonces; no inline scripts except nonce'd.
- Learner code runs only in Workers with no DOM access and no network (CSP `worker-src` + fetch disabled inside the worker).
- Auth uses httpOnly, Secure, SameSite=Lax cookies; no tokens in localStorage.
- Sanitise any rendered Markdown (content is trusted, but defense in depth).
